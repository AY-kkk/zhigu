## 0. 评审说明

### 0.1 用户问题界定（Job-to-be-Done）

| 维度 | 内容 |
|---|---|
| 目标用户 | ① 个人投资者：有自己关注的持仓或自选股，没有专职信息团队；② 投研人员：负责跟踪覆盖标的，需要向他人说明判断依据 |
| 场景 | 关注标的出现一个会不断发展的事件（如"A 拟收购 B"）：先有传闻，再有媒体报道和研报解读，然后公告确认、金额更正，或当事人否认，最后没了下文 |
| 痛点 | P1 **找不到源头**：几十篇转载，分不清谁先说、谁在转述；P2 **分不清轻重**：事实、观点、推测、传闻混在一起，看不出哪些可信；P3 **跟不上变化**：金额改了、被否认了、没下文了，旧结论还在脑子里；P4 **冲突无从判断**：公告否认而媒体坚持，没有并列对照；P5 **不知道与我何干**：事件和我关注的标的是什么关系、影响方向如何 |
| 期望结果 | 打开一个事件，**1 分钟内**能说清：最初来源是谁、事实经过哪些变化、哪些证据互相冲突、现在处于什么状态、对我关注的标的影响方向和可信度如何；**每个数字和结论都能点回原文**；事件状态一变就收到通知 |
| 评判基准 | 以下审计和补全都以"是否帮助用户完成上述 5 个判断，且判断可追溯"为准，与此无关的需求一律不加 |

## 1. 产品目标与范围

### 1.1 目标

- G1：把同一事件的多信源收敛成**一条事件时间线**，回答五个问题：最初来源、事实变化、证据冲突、当前状态、与关注标的的关系。
- G2：**可追溯**。页面上的每个关键数字（金额、比例、时间）和每个结论都能一键定位到原文引用或计算明细。
- G3：**变化即通知**。事件被更新、否认、更正或过期，只要导致结论变化，就通知订阅用户。

### 1.2 硬性约束

- C1：LLM **不产生**数字和结论。结论由确定性结论引擎计算，同样的输入必须得到同样的输出。
- C2：LLM 可以做的事**限于**：结构化抽取（必须带原文片段定位）、检索路由、对引擎结果的自然语言解释。【补】依据：草稿说"AI 仅做检索路由与解释"，与 R1、R2 实际需要的 NLP 抽取相矛盾，这里明确边界，详见 R8。
- C3：不提供投资建议（不输出买入、卖出、目标价），全站展示免责声明。【补】依据：题目要求覆盖"合规边界"。

### 1.3 非目标（本期不做）

- 不做交易、下单或组合管理；不做个股打分或荐股。
- 不做港美股（数据源以 A 股公告为权威兜底）。**待确认**
- 不做全网爬虫；只使用授权或公开权威信源。

### 1.4 交付范围（48 小时）【补】

依据：题目限时 48 小时，且要求提交可操作 URL 和演示视频。按以下分层确定范围。

| 层 | 内容 |
|---|---|
| 必交（P0） | 主链路可跑通：信源接入 → 归一化 → 合并与版本链 → 分级与权重 → 状态机 → 结论 → 站内通知 → 事件流和详情页；可追溯；回放演示 |
| 争取（P1） | 追问对话、通知偏好（免打扰/频率）、疑似合并确认、扶摇影响验证、用户笔记 |
| 规划（P2） | 外部推送渠道、Bigdata 交叉验证、产业链关联、权重离线标定 |

## 2. 名词定义【补】

依据：草稿中"事件、版本、证据、结论"等用词前后不一致，研发和测试需要统一口径。

| 术语 | 定义 |
|---|---|
| 信源（source） | 一篇原始材料：一条公告、一篇新闻、一份研报摘要、一条互动问答或一篇社区帖 |
| 根信源（root source） | 沿"转载 / 引用"链追溯到的最早原始材料；互相转载的多篇共用一个根信源 |
| 证据（evidence） | 从信源中抽取出的、与某事件相关的一条**可引用陈述**，包含原文片段、分级、权重和极性 |
| 事件（event） | 同一标的 + 同一事件主题的一条演化链 |
| 版本事件（version event） | 事件链上的一次变化：新增、更新、更正、否认、过期 |
| 事件状态（state） | 观察中 / 已确认 / 被否认 / 已过期（见 R3） |
| 结论（conclusion） | 影响方向 + 可信度 + 状态，由结论引擎计算 |
| 冲突（conflict） | 同一事件内，两条证据在同一关键参数或同一事实上的表述不一致 |
| 四时间戳 | 发生时间 occurred_at / 披露时间 disclosed_at / 抓取时间 fetched_at / 更新时间 updated_at（见 R5） |

## 3. 用户故事与核心流程

### 3.1 用户故事

| 编号 | 用户故事 | 对应痛点 |
|---|---|---|
| US-01 | 作为投资者，我添加关注标的并设置订阅，之后只看与我相关的事件 | P5 |
| US-02 | 作为投资者，我在事件流里一眼看到每个事件的当前状态、方向和可信度 | P2 P3 |
| US-03 | 作为投资者，我打开一个事件，能看到是谁最先说的，以及之后的每次变化 | P1 P3 |
| US-04 | 作为投资者，我能区分哪些是事实、观点、推测或传闻，并知道各自的权重 | P2 |
| US-05 | 作为投资者，当公告否认而媒体坚持时，我能看到两者并列对照 | P4 |
| US-06 | 作为投研人员，我能看到结论为什么变了、被哪条证据触发，并能点回原文向他人证明 | P1 P3 |
| US-07 | 作为投资者，事件被确认、否认、更正或过期时我会收到通知，而且不会被重复打扰 | P3 |
| US-08 | 作为投资者，我可以用自然语言追问"为什么可信度下降了"，回答带出处 | P2 P3 |
| US-09 | 作为评审 / 演示者，我能回放一个事件从传闻到确认（或否认、过期）的全过程【补】 | 交付要求 |

### 3.2 主流程（用户端）

1. 首次进入 → 设置关注标的（可一键加载示例标的池）→ 设置订阅规则和通知偏好。
2. 事件流首页 → 按"最近变化"查看关注标的的事件卡片（状态 / 方向 / 可信度 / 冲突数 / 未读标记）。
3. 点击卡片 → 事件详情：结论卡（可展开计算明细）→ 时间线 → 证据面板 → 冲突对照 → 结论历史。
4. 点击任意数字或引用 → 定位到原文片段；外链打开原文。
5. 收到通知 → 点击回到事件详情，并高亮本次变化 → 标为已读、忽略或静音。
6. （P1）在详情页打开追问对话 → 回答带证据引用。

### 3.3 主流程（后端）

```
信源接入(定时巡检 / 事件触发)
  → 去重(doc_id / content_hash)
  → 归一化(四时间戳 + 标的 + 事件类型 + 客体 + 参数实体，LLM 抽取 + 原文定位校验)
  → 根信源追溯
  → R1 同事件判定 ──┬─ 同一事件 → 写入版本链
                   ├─ 疑似 → merge_candidate（不自动合并）
                   └─ 不同 → 新建事件
  → R2 证据分级与权重 → 冲突检测（参数不一致 → conflict）
  → R3 状态迁移
  → R4 结论重算 → 与上一版比较 → 有变化则写入 conclusion_history
  → R7 变更分发 → 匹配订阅 → 去重 → 通知
```

### 3.4 分支流程【补】

依据：草稿只有主流程，下列分支都直接影响题目要求的"否认、更正、过期如何改变结论"。

| 编号 | 分支 | 处理 |
|---|---|---|
| B-01 | 疑似同一事件 | 不合并，不影响结论；在两个事件的详情页都展示"疑似关联事件"；（P1）用户或运营确认后合并，合并后重算两个事件的结论 |
| B-02 | 参数冲突（如金额 10 亿 vs 8 亿） | 合并但生成 conflict 记录；可信度封顶"中"（R4 冲突锁）；高等级信源给出更正时，事件标记"已更正"，冲突置为"已解决" |
| B-03 | 当事人否认 | 状态 → 被否认；结论置为"事件已否认，原结论作废"；推送通知 |
| B-04 | 否认后又出现新信源 | 事实级证据：新建事件链，并通过 predecessor_event_id 关联旧链；非事实级证据：挂入旧链作为证据，状态保持"被否认" |
| B-05 | 过期 | 推送一次"已过期"通知，之后停止推送；过期后又出现新信源时，按 B-04 的思路新建链（**待确认**：是否允许复活） |
| B-06 | 转载 / 同源 | 挂在同一根信源下，计权时按 1 条计（R4），时间线上折叠展示"另有 N 篇转载" |
| B-07 | 用户静音某事件 | 不推送，但站内事件流和详情照常更新 |

### 3.5 异常流程

见 §8，覆盖数据源失败、抽取失败、时间缺失、LLM 不可用等情况。

## 5. 核心业务规则

### R1 同一事件合并判定（在草稿基础上修正）

- R1.1 判定三元组：同一标的（证券代码 / 主体）+ 同一事件主题（事件类型 + 核心客体，如"A 收购 B"）+ 时间窗口满足条件。
- R1.2 【补】**时间窗口改为滑动窗口**：新信源的披露时间与**事件最近一个版本的披露时间**相距 ≤ 7 天（草稿原为"相距 ≤ 7 天"，没有说以谁为基准）。依据：收购、重组这类事件会持续数月，如果以首条信源为基准，会被拆成多条链，违背"一条时间线"的目标。**待确认**
- R1.3 满足三元组，并命中任一强关联即判为同一事件：① 引用同一原始信源（同一公告编号 / 同一报道）；② 信源之间有明确指代；③ 关键实体重合度 ≥ 0.6。
- R1.4 【补】重合度的计算：对归一化后的实体集合（标的、客体、参数实体）计算 Jaccard 相似度；金额按"数值 + 单位"归一，比例按小数归一。
- R1.5 输出三态：
  - 同一事件：满足 R1.3；
  - 疑似同一事件【补】：满足三元组但没有强关联，且重合度 ∈ [0.4, 0.6)；或标的映射置信度不足。**待确认**阈值；
  - 不同事件：其他情况。
- R1.6 金额、比例、时间等关键参数不一致**不阻止合并**，改为生成 conflict 记录；同一标的但客体不同 → 不合并。
- R1.7 【补】候选召回可以用向量相似度（同标的、窗口内 top-20），但**是否合并由上述规则决定**，不交给 LLM 判断。依据：C1 要求可复现。

### R2 证据分级与权重（保留草稿，修正一处冲突）

- R2.1 判定优先级：信源类型 > 是否具名 > 是否含可验证凭证 > 表述模态（"已 / 宣布"为事实语气，"或 / 可能"为推测语气，"据悉 / 网传"为传闻语气）。

| 分级 | 判定标准 | 分级系数 |
|---|---|---|
| 事实 | 法定披露或可验证的原始凭证（公告、监管文书、财报数据） | 1.0 |
| 观点 | 具名信源的主观判断或预测（研报评级、分析师观点） | 0.6 |
| 推测 | 没有凭证的推演（"或因""可能"类因果判断） | 0.3 |
| 传闻 | 来源不可考、非权威渠道、未经当事人确认 | 0.1 |

- R2.2 信源基础权重：法定披露 1.0 / 主流财经媒体 0.6 / 研报 0.5 / 一般媒体、互动平台 0.3 / 自媒体、社区 0.1（初始值，上线后标定）。
- R2.3 证据权重 = 信源基础权重 × 分级系数。
- R2.4 修正因子：
  - 当事人或公司确认：×1.2（封顶 1.0）；
  - 被更高等级信源明确否认：权重置 0，并标记 contested；
  - 【补】**时间衰减改为 14 天无新信源 ×0.8，并标记"信息陈旧"**，30 天进入过期评估（R3）。依据：草稿的衰减和过期同在第 30 天触发，衰减没有实际作用。**待确认**
- R2.5 user_annotation 不计权重，只并列展示。
- R2.6 【补】分级由规则判定，LLM 只提供"表述模态"和"是否具名"等特征，并且必须附原文片段（R8）。无法判定时，默认取**较低一级**并标记"分级存疑"。依据：宁可低估，也不高估可信度。

### R3 事件状态机（修正）

【补】依据：草稿把"更新"列为状态，把"已更正"列为终态。但更正之后事件仍会继续演化（例如更正金额后公告完成交割），所以把状态和版本事件拆开。

- R3.1 **状态集**：观察中（初始）/ 已确认 / 被否认（终态）/ 已过期（终态）。
- R3.2 **版本事件类型**：新增 / 更新 / 更正 / 否认 / 过期。每次版本事件都会让 version + 1，并触发 R4 重算。
- R3.3 迁移条件：

| 当前状态 | 触发条件 | 版本事件 | 新状态 |
|---|---|---|---|
| — | 首条信源 | 新增 | 观察中 |
| 观察中 | 出现事实级证据（法定披露或当事人确认） | 更新 | 已确认 |
| 观察中 / 已确认 | 新信源经 R1 合并进来 | 更新 | 不变 |
| 观察中 / 已确认 | 更高等级证据修正关键参数 | 更正 | 不变，并打上"含更正"标记 |
| 观察中 / 已确认 | 当事人或法定信源明确否认（否认优先于确认） | 否认 | 被否认 |
| 观察中 / 已确认 | 30 天无新信源，且没有待决冲突 | 过期 | 已过期 |

- R3.4 【补】存在待决冲突时暂不过期；但 60 天无新信源时**强制过期**，并在通知中说明"冲突未解决"。**待确认**
- R3.5 终态不可逆：翻案必须新建事件链，并关联前序事件（见 B-04）。
- R3.6 【补】公告"终止"（例如终止收购）不属于否认，而是一次"更新"，按新证据极性重算方向。**待确认**
- R3.7 【补】过期计时以**新信源的披露时间**为准，不用抓取时间。依据：补抓的历史旧闻不应让事件"复活"。

### R4 结论计算（确定性规则，补全公式）

- R4.1 结论 = 影响方向（利好 / 利空 / 中性）+ 可信度（高 / 中 / 低）+ 事件状态。
- R4.2 可信度分 = min(1, Σ 证据权重)。【补】"同源多篇按 1 条计"的具体做法：同一根信源下的证据只取**权重最大**的一条。
- R4.3 档位：≥ 0.8 为高；[0.4, 0.8) 为中；< 0.4 为低（阈值上线后标定）。
- R4.4 【补】**证据极性**（草稿缺失，R4 无法计算）：
  - 每条证据相对**具体标的**标注极性（同一收购事件，对收购方和标的方的极性可能不同）；
  - 来源按优先级：① 观点类证据取原文中明确的评级或方向；② 其他证据取"事件类型默认极性表"（例：业绩预增 = 利好，股东减持 = 利空，立案调查 = 利空）**待确认**：极性表内容；③ 以上都没有 → 中性；
  - LLM 可以给出极性建议，但必须附原文片段，且只在 ①② 都不适用时作为参考展示，**不参与计算**。
- R4.5 【补】影响方向公式：设 P = Σ 利好证据权重，N = Σ 利空证据权重。
  - P > 0 且 P ≥ 1.2 × N → 利好；
  - N > 0 且 N ≥ 1.2 × P → 利空；
  - 其他情况 → 中性。
- R4.6 冲突锁：存在 contested 证据对 → 可信度封顶"中"；状态为被否认 → 结论直接置为"事件已否认，原结论作废"；状态为已过期 → 保留最后结论，并标注"已过期，不再更新"【补】。
- R4.7 重算触发：新增证据 / 权重变化（含衰减）/ 状态迁移。重算后与上一次结论比较，方向、可信度档位或状态任一变化即写入 conclusion_history，并进入变更分发。
- R4.8 【补】每次计算都输出 calc_trace：参与的证据 ID、各自权重及拆解、命中的规则、P/N 值、可信度分。前端的"计算明细"直接渲染 calc_trace。依据：题目要求"关键数字与结论必须可追溯"。

### R5 四时间戳处理【补】

依据：题目明确要求体现四时间戳的处理，草稿只写了"打四时间戳"，没有规则。

| 时间戳 | 定义 | 获取方式 | 缺失 / 异常时 |
|---|---|---|---|
| 发生时间 occurred_at | 事件实际发生的时间 | 从正文抽取，同时记录精度（日 / 月 / 区间 / 预计） | 显示"未知"，**不用披露时间代替** |
| 披露时间 disclosed_at | 信源公开发布的时间 | 取信源元数据 | 用抓取时间代填，并标记"披露时间为推断值"，该信源不能作为"最初来源" |
| 抓取时间 fetched_at | 系统入库的时间 | 系统写入 | — |
| 更新时间 updated_at | 分两种：信源更新时间（原文被修订）和事件更新时间（最近一次版本事件） | 元数据 / 系统写入 | 信源更新时间缺失时留空 |

- R5.1 时间线主轴按**披露时间**排序；发生时间作为辅助标注。
- R5.2 **最初来源** = 事件内披露时间最早、且披露时间非推断值的根信源；时间相同时取信源等级更高的一条。
- R5.3 异常校验：
  - 披露时间晚于抓取时间 → 视为时钟异常，以抓取时间为准并记录告警；
  - "已发生"类事实的发生时间晚于披露时间 → 标记"时间存疑"；
  - 未来的发生时间允许存在，但必须标注为"预计"。
- R5.4 统一以 UTC 存储，以北京时间（UTC+8）展示。

### R6 与关注标的的关系【补】

依据：这是五个核心问题之一，草稿只列了 get_watchlist_relation 接口，没有规则。

- R6.1 关系类型：
  - 直接：事件主体就是关注标的；
  - 交易对手：事件客体是关注标的（例如被收购方）；
  - 关联：同一集团或产业链上下游（P2）。
- R6.2 关系来自结构化数据（证券主体映射），不由 LLM 推断。
- R6.3 同一事件对不同标的分别计算极性和方向（R4.4）。
- R6.4 （P1）影响验证：取扶摇行情，展示披露日前后窗口期 [-1, +3] 个交易日的相对基准涨跌幅，**仅供参考，不参与结论计算**。**待确认**：窗口长度和基准指数。

### R7 通知规则【补】

依据：草稿只有"结论变化 → 推送"，没有写明触发条件、去重和过期如何处理。

- R7.1 **触发推送**的变化：状态迁移（→ 已确认 / 被否认 / 已过期）、更正、影响方向变化、可信度档位变化。
- R7.2 **不推送**的变化：可信度档位内的分数波动、只增加转载。
- R7.3 匹配规则：事件涉及的标的在用户关注池中，且命中用户的订阅规则。
- R7.4 去重键为 user_id + event_id + conclusion_seq；同一事件 30 分钟内的多次变化合并成一条，内容以最新结论为准。**待确认**：合并窗口长度。
- R7.5 用户操作：
  - 已读：消除未读标记；
  - 忽略：关闭当前这条通知，不影响后续通知；
  - 静音：该事件不再推送，站内内容照常更新，可取消静音。
- R7.6 免打扰时段内的通知进入队列，时段结束后以汇总形式发送。
- R7.7 过期时只推送**一次**"已过期"通知，之后停止推送。
- R7.8 通知内容包括：事件标题、变化类型、新旧结论对比、触发证据摘要和跳转链接。

### R8 AI 角色边界【补】

依据：C1 和 C2，以及题目要求 README 说明 AI 角色、提交 AI 使用与验证记录。

| 任务 | 是否允许 LLM | 约束 |
|---|---|---|
| 结构化抽取（标的、类型、客体、参数、时间、模态） | 允许 | 输出必须带原文片段偏移（start/end）；**原文中找不到的数字直接丢弃**；输出结构不合法时重试 1 次，仍失败则进入"待处理"，不参与计算 |
| 证据分级 | 只提供特征 | 最终分级由 R2 规则决定 |
| 同事件判定 | 只用于召回 | 判定由 R1 规则决定 |
| 结论、权重、可信度 | **禁止** | 由结论引擎计算 |
| 追问对话 | 允许（路由 + 解释） | 只能基于工具返回的内容回答；**回复中出现的每个数字都必须出现在工具结果中**，否则拦截并重新生成，仍不通过则只返回结构化结果；无证据时回答"未找到相关证据"；拒答投资建议类问题 |
| 记录 | 必须 | 每次调用记录模型和 prompt 版本、输入哈希、输出、校验结果（F-31） |

## 8. 边界与异常处理【补】

依据：草稿没有这部分；题目要求测试"数据/接口异常"。

|---|---|---|---|
| E-01 | iFinD 超时或不可用 | 重试 → 熔断 → 公告降级到巨潮；新闻和研报暂缺 | 横幅"部分信源暂不可用"；受影响事件显示"信源覆盖不完整" |
| E-02 | 所有数据源不可用 | 停止入库，已有事件和结论照常展示 | 横幅显示最近一次成功更新的时间 |

| E-04 | LLM 抽取失败或输出不合法 | 重试 1 次，仍失败则标记"待处理"，不参与计算 | 详情页显示"N 条信源待处理" |
| E-05 | 抽取出的数字在原文中找不到 | 丢弃该字段，记录到 extraction_run | 无 |
| E-06 | LLM 服务不可用 | 抽取暂停并排队；对话不可用；**结论引擎不受影响** | 对话入口显示不可用 |

| E-10 | 标的无法映射 | 不归入任何关注标的，进入待处理 | 无 |
| E-11 | 重复入库 | 幂等去重 | 无 |
| E-12 | 一个事件的证据超过 200 条 | 分页加载；计算不受影响 | 折叠展示 |
| E-13 | 同一事件短时间内频繁变化 | 按 R7.4 合并通知 | 一条通知 |
| E-14 | 事件终态后又来新信源 | 按 B-04 / B-05 处理 | 显示"关联前序事件" |
| E-15 | 用户未关注任何标的 | 引导设置 | 空态 |

## 9. 非功能需求【补】

依据：草稿没有这部分。以下数值是演示阶段的建议默认值，全部**待确认**。

### 9.1 性能

| 指标 | 目标 |
|---|---|
| 事件流首屏（≤ 50 条） | P95 ≤ 1 秒 |
| 事件详情（≤ 200 条证据） | P95 ≤ 1.5 秒 |
| 单个事件结论重算 | ≤ 200 毫秒 |
| 对话首字 / 完整回答 | ≤ 3 秒 / ≤ 15 秒 |
| 公告从披露到通知 | ≤ 巡检周期 + 2 分钟 |

### 9.2 并发与容量

- 演示环境支持 50 名用户同时在线；单标的日均信源按 500 条设计。**待确认**

### 9.3 安全与合规

- 不输出投资建议，全站展示免责声明（C3）。
- 传闻类证据必须有显著标签；在任何页面上都不能把传闻呈现为事实。
- 研报和商业数据遵守 §7.6。
- API 密钥只放在服务端，不下发到前端，也不写进代码仓库。
- 用户数据按 user_id 隔离；日志不记录用户笔记正文。
- 回放和演示数据与真实数据隔离，并带水印。

### 9.4 兼容性

- 桌面端 Chrome、Edge、Safari 最新两个版本。
- 移动端宽度 ≥ 375px 时可正常阅读（非主要场景）。

### 9.5 可观测

- 指标：各信源拉取成功率和耗时、入库量、同事件判定三态分布、待处理队列长度、抽取失败率、数字校验丢弃率、结论变更次数、通知发送量和去重率。
- 日志：结构化日志，贯穿 trace_id（信源 → 证据 → 结论 → 通知）。

### 9.6 可复现

- 结论引擎是纯函数：同样的证据集合 + 规则版本 → 同样的结论。
- 规则参数（阈值、权重）配置化并带版本号，calc_trace 中记录规则版本。
- 系统时钟可注入，供回放和测试使用。

## 11. 测试要点（供 QA 评审）

### 11.1 主链路（端到端）

- 用回放样例集跑通三条路径（AC-12），逐步核对状态、版本号、结论、conclusion_history 和通知。
- 用真实数据抽样：选 3 个近期有公告的关注标的，核对入库、合并和展示。

### 11.2 规则边界值

| 规则 | 用例方向 |
|---|---|
| R1 时间窗口 | 距最近版本 7 天整 / 7 天 + 1 秒；链式跨度超过 7 天但每步 ≤ 7 天 |
| R1 重合度 | 0.39 / 0.40 / 0.59 / 0.60；同标的不同客体；参数冲突 |
| R1 强关联 | 同一公告编号的不同转载；有明确指代但实体重合度低 |
| R2 分级 | 各信源类型 × 模态组合；具名研报用了"据悉"措辞；无法判定时降级 |
| R2 修正 | 确认 ×1.2 封顶 1.0；被否认后权重为 0；14 天衰减 |
| R4 可信度 | 0.399 / 0.4 / 0.799 / 0.8；同源 5 篇只计 1 条 |
| R4 方向 | P = 1.2N 恰好相等；P = 0 且 N = 0；只有一方有证据 |
| R4 冲突锁 | 可信度分 ≥ 0.8 但存在 contested → 显示"中" |

### 11.3 状态机

- 逐条覆盖迁移表，外加非法迁移：终态 → 其他状态必须被拒。
- 同一批次内同时到达确认和否认 → 否认优先。
- 有待决冲突时第 30 天不过期，第 60 天强制过期。
- 过期计时以披露时间为准：补抓一条 40 天前的旧闻不会重置计时。

### 11.4 时间处理

- 发生时间缺失、披露时间缺失、披露时间晚于抓取时间、发生时间晚于披露时间、未来的"预计"时间。
- 时区：UTC 存储、北京时间展示，跨日边界（UTC 16:00）。
- 最初来源：两条披露时间相同时取高等级；推断时间的信源不能成为首发。

### 11.5 通知

- R7.1 和 R7.2 的正反用例；30 分钟合并窗口；静音、忽略、已读的行为差异；免打扰汇总；过期只通知一次。
- 未关注的标的不通知；取消关注后不再通知。

### 11.6 AI 可追溯与幻觉

- 构造原文不含的数字，验证抽取阶段丢弃（E-05）。
- 诱导对话输出无出处的数字或结论，验证被拦截。
- 投资建议类问题（"要不要买""目标价多少"）→ 拒答。
- 无证据问题 → "未找到相关证据"。
- 抽查 extraction_run 记录是否完整。

### 11.7 数据 / 接口异常

- 模拟 iFinD 超时、5xx、空返回、字段缺失、限流 → 重试、熔断、降级到巨潮、横幅提示。
- LLM 超时或不可用 → 对话降级，结论照常。
- 重复推送同一公告 → 幂等去重。

### 11.8 合规边界

- 检查数据库中没有研报全文字段内容。
- 传闻标签在事件流、详情、通知和对话四个位置全部可见。
- 免责声明在所有页面可见；演示数据带水印且不混入真实数据。
- 前端包和代码仓库中没有 API 密钥。

### 11.9 前端状态与兼容

- 每个页面的空态、加载态、异常态、终态横幅。
- 三个浏览器 + 375px 宽度下的冒烟测试。
