| P-03 工具多轮 | 两协议各跑工具请求→结果回传→最终回答；多个调用ID正确配对；Responses使用call_id而非误用item.id；未执行工具不得有伪造结果 |
| P-04 上下文 | Responses完整回放必要Items，含适用模型的reasoning/encrypted续轮项；任务间不串；禁previous_response_id/conversation；不把续轮私有内容写进报告/普通日志 |
| P-05 预算与幂等 | 两协议共用调用上限/Token/费用；回放输入、推理输出不漏计；usage缺失unknown；跨协议重复request_id拒绝，不重复计数或出站 |
| P-06 失败与权限 | 错Key/429/超时/拒绝/截断/incomplete均类型化；取消与scope两入口一致；store=false，Responses禁止background与所有内置工具，不能因换协议绕限制 |
| P-07 真实启用 | 当前拟启用的每个协议配置均需实际Go+Python capability与live链路证据；未测的配置不能启用；后台不能以“代码支持双协议”冒充两路live都通过 |

live范围在D-02预先冻结：有 Responses 可用凭据则必须纳入 live，按 SPEC §2.3 计数。如只有一种协议的有效凭据，可以签收该路线的样机，但另一种必须已完成受控实现/集成测试，并在最终报告明确“live未验证”；不要求擅自申请第二份付费账户。若声明两路均可实用，则两路均须真实验证。既有20次live样本总数不自动翻倍：仅一条路线启用时全用该路线；两条时10个输入各以两种协议各跑1次，并分别汇总，不能将某一路全失败隐藏在总数里。两路均验收时每路至少9/10流程完成，其余质量要求不变。Tushare 积分不是 live 数据前置；数据 live 走东财/新浪+巨潮。

## 3. 测试入口与执行顺序

### 3.1 开发者必须提供的统一脚本

从仓库根目录运行以下命令。**这些是待实现入口，不是本次已运行命令。**

```sh
bash app/scripts/verify-stage-b.sh offline
bash app/scripts/verify-stage-b.sh integration
bash app/scripts/verify-stage-b.sh live
bash app/scripts/verify-stage-b.sh all
```

- `offline`：Schema/单位计算/受控上游/质量集等，不访问真实供应商，不发生外部费用。
- `integration`：真实 Go、Python、Eino/Harness、PostgreSQL，受控外部模型/数据，不用假 ResearchClient；测并发、取消、重启、权限与浏览器基本链路。
- `live`：确认 D-01～D-07 与费用后才访问真实供应商；对预先声明的拟启用协议配置跑 capability、真实数据、浏览器全链路和20次样本。未选另一协议记live未验证，不伪装通过或跳过已声明的必需测试。
- `all`：依次执行三者，不能为了通过自动补假凭据、自动采购或默认 skip live。
- 退出码：0=本次命令对应测试通过；1=断言失败；2=环境/凭据/依赖/授权阻塞；3=必需测试跳过/空集/证据不全。退出0仍不等于用户已签收。

脚本要收集以下底层命令的实际输出，不能用自己的 summary 替换：

| 工作目录 | 命令 | 必要补充 |
|---|---|---|
| `app/server` | `go test ./...` | 全量回归 |
| `app/server` | `go test -race ./service/finance/...` | 实际 finance 包路径若调整，manifest中明确映射 |
| `app/research-service` | `uv run pytest tests -q` | 导出 JUnit/测试数；实际 Harness测试必跑 |
| `app/web` | `npm ci`、`npm run build`、`npm run test:e2e` | 浏览器运行时需可用；缺 Chromium是blocked，非pass |

集成测试必须使用隔离的测试数据库/临时目录，不能删用户开发数据库。故障注入只针对测试进程/指定模拟上游，不停用户其他服务。测试可用临时 HTTP upstream 记录真实请求数，禁止用自增局部变量代替代码路径执行证明。

### 3.2 三种必须被识破的“伪通过”

1. 将 Harness 初始化替换成空对象：B-14 必须失败；仅 import 测试不够。
2. 去掉引用/单位检查或把验证结果固定 true：对应 B-21/B-22/B-30 的受控负例必须失败；修改测试分支后恢复，不改生产运行实例。
3. 停掉 Python、使 live Key 无效或数据源无正文：集成/live 验收必须失败或blocked；不得得到 fixture完整报告。

不要求建设通用 mutation testing 平台；上述局部负控用可恢复测试配置/测试替身即可。反向验证用于确认测试能发现错误，不将临时破坏留进交付代码。

## 4. 证据包格式

开发交付时生成 `artifacts/stage-b/<UTC时间>-<shortSHA>/`。本次不提前创建结果文件。私有内容默认不提交 Git，确需存档遵守来源许可；公共包只留脱敏摘要和 hash。原始付费正文不打包公开传播。

```text
manifest.json                  # 模式、基线、D/G/B状态、每项测试节点和证据引用
baseline.json                  # Git SHA、dirty patch hash、runtime与依赖锁hash
commands.jsonl                 # cwd/command/start/end/exit_code，秘密环境变量不展开
tests/                         # Go JSON、pytest JUnit、浏览器报告与失败截图
capabilities.json              # 每protocol的实现/集成/live分项、config digest、实际request关联
traces.redacted.jsonl           # run/task/request、阶段时间、上游request_id或响应hash
usage.redacted.jsonl            # 预占/实耗/unknown、工具grant、connector HTTP计数
quality/cases.json              # 冻结30例，含期望与证据引用
quality/results.json           # 自动断言、人工标签、标注人/复核人
live/runs.json                 # 冻结10输入×2的所有结果，不只成功样本
summary.md                     # 完成/阻塞/失败、局限、待决事项，不包含Key
```

`manifest.json` 最低字段：spec_version、git_sha、working_tree_hash、runtime_versions、lock_hashes、mode、started_at、finished_at、prerequisites、gates、requirements、commands、limitations。每个 requirement 含 B-ID、tests[]、passed/failed/skipped 数、evidence[]、review_status；不得用一个总 boolean 覆盖所有分项。

真实调用证据优先使用供应商 request_id；没有时使用出口时间、目标允许主机、响应 hash、对应账本进行关联，并注明无供应商 ID。不得为补证据记录 Key、完整授权头或用户私有观点。供应商账单/计价未知则写 unknown，不伪造费用。
